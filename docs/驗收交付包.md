# 第 04 組｜驗收交付包

本文件專為口頭驗收、現場展示與教師追問整理。交付資料位於本專案
`docs/`、`.github/` 與 GitHub PR 中。

## 一、專案定位

本專案是一個以 Firebase 為後端的個人課堂工作台：

- 提供 Google、電子郵件／密碼註冊與登入。
- 支援密碼重設與兩種登入方式帳號連結。
- 提供個人任務的新增、編輯、刪除、狀態更新、搜尋與篩選。
- 使用 Firestore 即時監聽同步任務。
- 透過 Firestore Rules 確保每位使用者只能存取自己的資料。

目前不是共用工作區、多人協作看板或管理者系統；這些功能不屬於 MVP。

## 二、專案如何開啟

### 必要環境

- Node.js 22.12 以上；專案以 Node.js 24 驗證。
- Java 21 以上；執行 Firebase Emulator 測試時需要。
- Playwright Chromium；執行瀏覽器 E2E 測試時需要。

### 安裝與啟動

在專案根目錄執行：

```powershell
npm ci
npm run dev
```

瀏覽器開啟：

```text
http://127.0.0.1:5173/
```

正常模式會連到 Firebase 正式專案：

- 專案 ID：`uxd2026-413580134`
- Auth：Google、Email/Password
- Firestore：`asia-east1`

### 模擬器模式

若要在本機模擬 Authentication 與 Firestore，建立或修改 `.env.local`：

```text
VITE_USE_EMULATORS="true"
```

若測試或模擬器出現 Java 錯誤，確認：

```powershell
java -version
```

正確結果應為 Java 21 或更新版本。若找不到或找到 Java 8，可安裝
Eclipse Temurin JDK 21：

```powershell
winget install --id EclipseAdoptium.Temurin.21.JDK --exact
```

## 四、User Story 與驗收標準

### US-01：註冊與登入

**使用者故事**

身為課堂使用者，我希望能以電子郵件／密碼註冊、登入、登出與重設密碼，
以便安全地進入個人工作區。

**Acceptance Criteria**

- 無效電子郵件、過短密碼或錯誤憑證會顯示明確錯誤。
- 成功註冊會建立 Firebase User 與 `users/{uid}` 個人資料。
- 登入後可進入工作區，登出後回到登入畫面。
- 未登入無法讀取或建立個人資料與任務。

### US-02：連結 Google 與密碼帳號

**使用者故事**

身為已登入使用者，我希望能將 Google 與密碼連結到同一個帳號，
以便使用任一登入方式都能看到相同資料。

**Acceptance Criteria**

- Google 先建立帳號或 Email/Password 先建立帳號，兩種流程都保留原 UID。
- 已連結的 provider 可以在登入頁使用。
- 不會因相同 Email 就自動合併兩個既有 UID。
- Provider 衝突或憑證衝突會顯示可理解的錯誤。
- 帳號連結後，任務仍位於相同 `users/{uid}/tasks` 路徑。

### US-03：個人任務 CRUD

**使用者故事**

身為已登入使用者，我希望能新增、編輯、篩選、搜尋、更新狀態與刪除任務，
以便管理自己的課堂進度。

**Acceptance Criteria**

- 任務標題不可空白，最多 160 字元。
- 補充說明最多 2,000 字元。
- 狀態僅能是 `todo`、`doing` 或 `done`。
- 建立與更新必須帶有合法的 `ownerUid`。
- `ownerUid` 與 `createdAt` 建立後不可修改。
- 使用者不能讀取、更新或刪除另一個 UID 的任務。
- 刪除前會顯示確認視窗。

### US-04：即時同步與錯誤狀態

**使用者故事**

身為工作中的使用者，我希望任務變更能即時顯示並具備清楚的錯誤／空狀態，
以便知道目前是否已連線及資料是否成功。

**Acceptance Criteria**

- `onSnapshot` 更新會顯示新增、編輯、狀態變更與刪除。
- 無任務、搜尋無結果、正在載入與權限失敗都有對應畫面。
- 連線失敗不會讓「新增任務」顯示成成功操作。
- 桌面與窄螢幕版面都可操作。

## 五、API／介面合約

本專案沒有自行建立 REST API，而是直接使用 Firebase Web SDK。

### Authentication API

| 功能 | Firebase SDK |
| --- | --- |
| 註冊 | `createUserWithEmailAndPassword` |
| 登入 | `signInWithEmailAndPassword` |
| Google 登入 | `signInWithPopup` |
| 登出 | `signOut` |
| 密碼重設 | `sendPasswordResetEmail` |
| 更新資料／密碼 | `updateProfile`、`updatePassword` |
| 連結登入方式 | `linkWithPopup`、`linkWithCredential` |

### Firestore 資料路徑

| 資料 | 路徑 | 權限 |
| --- | --- | --- |
| 個人資料 | `users/{uid}` | 只有本人 |
| 個人任務 | `users/{uid}/tasks/{taskId}` | 只有本人 |

### 個人資料合約

```ts
type UserProfile = {
  uid: string;
  displayName: string; // 1-80 字元
  createdAt: Timestamp;
  updatedAt: Timestamp;
};
```

### 任務合約

```ts
type TaskStatus = "todo" | "doing" | "done";

type Task = {
  ownerUid: string;
  title: string; // 1-160 字元
  notes: string; // 0-2,000 字元
  status: TaskStatus;
  createdAt: Timestamp;
  updatedAt: Timestamp;
};
```

任何功能變更都必須同時更新：

1. 前端 TypeScript 型別。
2. `firestore.rules`。
3. Emulator 測試。
4. README 或 API 合約文件。

詳細合約請參考：

- `docs/api-contract.md`
- `firestore.rules`
- `src/main.ts`
- `src/firebase.ts`

```text
登入畫面
  -> Firebase Auth
  -> 建立 users/{uid}
  -> 新增 users/{uid}/tasks/{taskId}
  -> Firestore Rules 驗證 ownerUid
  -> onSnapshot 即時回傳畫面
  -> Emulator / Playwright 自動驗證
```

## 七、細節掌控與微調

驗收時需展示：

- 桌面與手機版面。
- 任務新增／編輯對話框。
- 搜尋與四種狀態篩選。
- 任務狀態下拉更新。
- 刪除確認與成功／錯誤提示。
- 登入／註冊切換。
- Google 連結與密碼連結畫面。
- Loading、空狀態、權限失敗與一般錯誤。
- 未登入或其他 UID 不可讀取私人資料。

若老師追問為何不會被跨域讀取，回答：

> Firestore Rules 會驗證路徑 UID 與 `request.auth.uid` 相同，前端只是呼叫
> SDK 的介面；真正的存取控制不依賴隱藏 API key，而是由 Authentication 與
> Rules 強制執行。

## 十二、老師可能追問的答題重點

### 為什麼可以確認這是全端專案？

因為功能從 React/Vite 類型的瀏覽器介面經 Firebase Auth、
Firestore SDK、Firestore Rules 一路落到資料庫權限與自動測試。

### 為什麼這份專案不是只做前端假資料？

登入、UID、個人資料與任務都存在 Firebase；帳戶資料與權限由 Auth/Rules
控制，任務也透過 Firestore 即時監聽。

### 如何防止跨使用者操作？

所有資料路徑都包含自己的 UID；Rules 比對
`request.auth.uid == uid`，並驗證建立／更新的資料合約。

### 如何控制 AI 產出？

使用 repository 級 `.github/copilot-instructions.md` 固定架構、資料格式、
命名、安全與測試規則；功能變更透過 PR、雜湊與自動測試審查。

### 是否有控制範圍蔓延？

目前 README 明確將共用資料／成員管理排除在目前階段；新增功能必須有
User Story、Acceptance Criteria、資料合約、Rules 與測試。
